# Evidence calibration: code

Apply this when the evidence includes existing code — not a document, not a conversation, the code itself.

**If you're deriving from an unmapped area of code, don't boil the ocean.** A document has a bounded size you can read in full before converting anything; a codebase doesn't. Pick one vertical slice first — one feature end-to-end, or one epic's worth of entry points — and take it from entry point through to data and business logic before moving to the next slice. A narrower first pass means fewer places for the risk below to hide undetected, and gives the person a smaller, checkable batch to confirm before you continue.

The core risk here is different and sharper than a document's ambiguity problem: **confusing what the code happens to do with what the system is supposed to do.** Code is executable ground truth for mechanism — it doesn't lie about what runs. It says nothing reliable about intent. A validation branch, a hardcoded limit, an odd sequencing of two calls could be a deliberate rule, or a bug, a workaround, or dead code. Getting this wrong is worse than a misread document: a misread bug canonized as a `business_rule` tells the next reader of the graph that the bug is correct, and they'll build on top of it.

Tiered confidence specific to code:
- **High — write directly.** Structural, shape-level facts unambiguous regardless of intent: a column's name/type/nullability, an explicit foreign key constraint, a route's path and method, a request/response shape from a type or serializer. Check for a separate validation file too — application-layer constraints (length bounds, format checks) routinely live outside the schema, precisely because the database doesn't need to enforce them to function. For every field, check for a corresponding validation file (`<module>.validation.ts`, a Zod/Joi schema, a serializer) before treating the Constraints column as complete. This tier is only high-confidence when the fact comes from that specific entity's own definition — not from how the rest of the codebase typically shapes similar entities. A codebase where most models share a convention (an int PK, a bytes/JSON value column) will have real exceptions, and completing an unread entity's shape from its neighbors' pattern produces a fact that looks structural and unambiguous but was never actually checked. Read the specific struct, message, or migration for the entity in front of you before writing its fields — don't finish the shape from what similar entities elsewhere in the graph look like.
- **Real, but incomplete — write what you can, then ask.** Business logic consistently enforced across every code path, backed by a test, is high confidence for a `business_rule`'s **Statement** — the code proves the rule holds. It's zero confidence for **Rationale** — code doesn't explain why, only what, even when a test exists. A test strengthens confidence in the Statement; it still isn't Rationale. The only thing that counts as Rationale evidence is an explicit statement of *why* — a comment, a test description, a commit message — not the mere presence of a test or the behavior's consistency. Write the Statement, flag Rationale as unknown, ask rather than inventing a plausible justification.
- **Low — stop and flag, don't canonize.** Anything that could plausibly be unintentional: no test coverage, a check firing on only one of several similar code paths, anything that reads like a workaround, or behavior contradicting another node. Surface as "found in code, unclear if intentional." When following up on a flagged item, use *Elicitation* (in `SKILL.md`) for that exchange — one question at a time, not a batch.

Feature boundaries don't come from file or folder boundaries. Code is organized by technical layer or module, not by product capability. Look for entry points — route handlers, command handlers, queue consumers, cron jobs — and trace outward from there to find a feature's real boundary. A single feature will often span several files; a single shared utility file may be touched by many unrelated features and isn't itself a feature.

Epics have the same problem, one level up. A folder like `services/notifications/` is a technical grouping, not necessarily a product domain — don't infer epic assignment from directory structure. Draft the features first, then either ask the person how they'd group them or leave epic assignment for a short follow-up conversation once a few features exist to group.

Product-level framing — `traverspec/about.md`'s Problem/Solution/Goals/Non-Goals, `traverspec/constitution.md`'s operational standing rules — isn't something code can tell you. Code shows what was built, not what the product is for or what it deliberately chooses not to do. Don't reverse-engineer these from code structure or naming; ask the person directly, or leave them empty and say so.

Mapping code facts to edges: trace actual reads/writes for `mutates`/`reads`; the entry point's own route mapping for `triggers`; a literal enqueue/event-emit/cron registration for `dispatches` — don't skip this just because it's "an implementation detail," it's exactly the causality fact prose tends to miss and code makes explicit; an explicit constraint in a migration for `foreign_key`; one feature's entry point calling into logic another feature's entry point also relies on, or requiring another feature's data/state to exist first, for `depends_on`; a code path that implements a `business_rule` you've already written (or are writing now) with a confirmed Statement, for `enforces`.
